# Payment Invariants

Business rules that must hold at all times, regardless of failures, replays or
concurrency. The saga, ledger and outbox designs exist to enforce these.

## Core invariants

1. **Amount cannot change after creation.** A payment's amount is set at
   creation and is immutable throughout its lifecycle.

2. **Currency cannot change.** The currency is fixed at creation. Cross-currency
   operations are out of scope.

3. **Merchant cannot change.** The merchant comes from the authenticated token
   and is written once.

4. **Customer cannot change.** The customer association (when present) is set at
   creation and never modified.

5. **Status follows a finite state machine.** Valid transitions are defined in
   `PaymentSagaStateMachine`. An illegal transition is rejected, never silently
   applied. See [SAGA.md](../../docs/SAGA.md) for the full state diagrams.

   ```
   Payments:  PROCESSING → AUTHORIZED → SUCCESS → REFUND_PENDING → REFUNDED
                         ↘ FAILED       ↗ CANCELLED
   Payouts:   PENDING → IN_TRANSIT → PAID → RETURNED
                       ↘ FAILED
   ```

6. **Financial data is append-only.** Ledger entries are never updated or
   deleted. Corrections are new entries (compensating postings). Outbox messages
   are append-only and published exactly once.

7. **Payment IDs are globally unique.** Generated by the application as random
   UUIDs, exposed with a `pay_` prefix. No coordination across replicas is
   needed. See [ADR-001](../adr/ADR-001-payment-identifier.md).

8. **Every payment is auditable.** Every saga step, processor call, ledger
   posting and webhook delivery attempt is recorded with timestamps. The full
   history is available through `GET /api/v1/payments/{id}/saga`.

## Financial invariants

9. **Double-entry balance.** Every ledger transaction is a balanced set of
   debit/credit entries that sum to zero. The ledger rejects unbalanced
   transactions at the application level. Verified by the reconciliation:
   `debits − credits = 0.0000` per currency.

10. **A payment is settled at most once.** Even if the `SETTLE_PAYMENT` command
    arrives under different command IDs, the ledger posts exactly one settlement
    per payment (a business-key guard).

11. **Concurrent balance operations are serialized.** Refund holds and payout
    holds both lock the merchant account row (`SELECT ... FOR UPDATE`) before
    checking the balance. Two concurrent operations cannot both spend the same
    funds.

12. **Exact decimals end to end.** `BigDecimal` in Java, `NUMERIC` in Postgres,
    typed JSON parsing. Amounts never pass through `double`. A trailing-zero fix
    ensures `75.50` stays `75.50`.

## Consistency invariants

13. **At-least-once delivery, exactly-once effects.** Messages may be delivered
    more than once. Every consumer deduplicates: `processed_commands` (ledger),
    `processed_events` (webhook, notification), idempotency keys (processor,
    payment API).

14. **The outbox guarantees atomic state-and-message.** A state change and its
    outgoing message commit in the same database transaction. The relay publishes
    afterwards, never losing a message and never sending one for a rolled-back
    change.

15. **Compensation before the pivot, retry after it.** Before the capture (or
    bank transfer), failures are compensated (void, release hold). After it,
    steps are only retried. At the pivot, an unknown outcome is parked for an
    operator — never guessed.

16. **Reversal by key closes the authorization gap.** If an authorization
    answer is lost, the saga reverses by naming the original idempotency key.
    The processor voids the authorization if it exists, or blocks it if it
    arrives later.

## Payout invariants

17. **Only payable funds can be paid out.** The payable balance excludes
    settlements younger than the payout delay (T+2 by default), preserving a
    refund buffer. The ledger enforces this under its row lock.

18. **A bank return is booked.** Payout sagas stay open for a return window
    (5 days). A returned transfer is posted back to the merchant's balance
    (`RETURN_PAYOUT`).

19. **One payout per merchant per currency per batch day.** A unique index
    prevents a re-run of the batch from creating duplicates.

## Verification

These invariants are checked daily by the **reconciliation service**, which
compares the processor's settlement report, the ledger's transactions, and
payment/payout statuses. Any disagreement is classified by type and an alert
fires until the day is re-run clean.

On the load-test day (2,750,997 payments): captures = settlements = completed
payments, refunds matched, `debits − credits = 0.0000`, 0 sagas stuck.
