# ADR-001: Payment Identifier Strategy

## Status

Accepted

## Context

Payments need identifiers that are:

- globally unique without coordination, so any service replica can create them;
- safe to expose through the API: not guessable, and revealing nothing about volumes;
- recognisable at a glance in logs, support tickets and webhook payloads;
- efficient as a Postgres primary key.

Options considered:

1. Database auto-increment
2. UUIDv4 (random)
3. UUIDv7 (time-ordered)
4. ULID

## Decision

- **Internal identifier:** a UUID generated by the application, stored as Postgres `UUID`.
  Generation sits behind the `IdGenerator` interface; the current implementation
  (`UuidGenerator`) produces random UUIDs (v4).
- **Public identifier:** the same UUID with a type prefix, `pay_<uuid>`. The API returns it,
  webhooks carry it, and every endpoint that takes a payment id requires it
  (`IdentifierService.parsePaymentId`). Ids without the prefix, or of another type, are rejected
  with 400.

Other services follow the same pattern: merchants, ledger accounts and sagas use UUIDs, and the
processor issues prefixed ids (`auth_…`, `re_…`).

## Rationale

Database auto-increment was rejected:

- sequential ids expose volumes and invite enumeration of other merchants' payments;
- a sequence needs the database before an id exists, and doesn't merge across instances.

UUIDs are generated anywhere without coordination, and a random UUID can't be guessed. The
`pay_` prefix makes an id's type obvious wherever it appears. It also stops one kind of id being
passed where another is expected, the convention Stripe popularised.

UUIDv7 and ULID embed a timestamp, so new keys are inserted near each other in the primary-key
index. Random v4 keys land anywhere in the index, which costs page splits and cache misses at
high insert rates. At this project's volumes the difference doesn't show, so the simpler,
universally supported v4 is used. ULID was set aside because its tooling in the Java ecosystem
is less common and Postgres has no native type for it.

## Consequences

- Any replica of any service can create ids independently; ids are unique across services,
  regions and environments.
- Public ids are opaque and typed; internal code and databases use plain UUIDs.
- Moving to UUIDv7 for better index locality is a change to `UuidGenerator` alone (for example
  with `java-uuid-generator`, or the JDK once it supports v7). Existing v4 ids stay valid, since
  both are standard UUIDs in the same column.
